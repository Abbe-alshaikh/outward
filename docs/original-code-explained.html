1. Big picture: what is this?

outward is a batch worker that runs in a container. Each time it runs, it asks the BankWorks Oracle database which "outward" integration tasks are pending. For each task it pulls the file content (a BLOB/CLOB) out of the database, writes it to a mounted network share so BizTalk can pick it up, and can also write an archive copy and run "successor" steps. Finally it tells the database the task is done.

In short: database → files on a share. "Outward" means data leaving the bank system for downstream integrations.

4. Successors: the optional extra step

A task row can set OUTWARD_SUCCESSOR. In that case the file just written is not only data, it is also instructions:

  • hshl: the written file is a shell script, run with sh <file>. Exit code 0 and empty stderr gives status 002 (OK). Anything else gives 003 (failed).
  • hcsv / hbin: the written file is a manifest. Each line is §-separated:
    KIND § SQL_OR_TABLE § ? § DIR § FILENAME § [STATUS] § [ADDITIONAL_DATA]
    If KIND is TABLE or VIEW, the SQL becomes select * from X. Otherwise column 1 is the raw SQL. Every line produces one extra file: a tab-separated CSV for hcsv, or the first column's LOB for hbin.
  • Any other value is ignored (status 002).

            end
            S-->>H: bytes written
        end
        H-->>C: (count, total_size, last status, last additional_data)
    else other
        C-->>W: (0, 0, "002", "")
    end
    C-->>W: totals are added to file_count / file_size

7. Gotchas I noticed while reading

  1. The "not visible until DB completion" guarantee is weaker than the docstring says. move_file publishes the file before complete_task commits. If the process dies in between, BizTalk already has the file, the task gets reset on restart, and the file is produced again (a possible duplicate).
  2. requirements.txt is empty. The code needs oracledb, pandas, and okq8common.
  3. Hidden globals: handle_task/main use bw3, config, and logger, which are only created under if __name__ == "__main__". Importing app from tests or another module gives a NameError.
  4. handle_file with an empty manifest: completion_status is never assigned, so you get an UnboundLocalError. With many lines, only the last line's status is kept.
  5. get_task returning an empty DataFrame makes .iloc[0] raise IndexError. Only a non-DataFrame result is handled.
  6. ARCHIVE_DATA being NULL while ARCHIVE_FILENAME is set crashes write_lob (None.getchunksize()).
  7. Bare except: in write_successor_data swallows the real Oracle error. Only "Error processing file" gets logged.
  8. Trust boundary: the database decides which stored procedure is called (INTEGRATION_NAME), which SQL runs (manifest), and which shell script runs (hshl). That's fine if the DB is fully trusted. Just be aware that DB contents act as code here.
  9. config.app.heartbeat.*, db_timeout, and oracle_client are not used by this repo. They are presumably used inside okq8common, or not at all.
  10. Small things: the set_container_startup docstring says it returns a DataFrame, but the annotation says bool. file_count is passed twice in the completion tuple, which is probably "expected vs. written". The write_task_to_disk docstring mentions a ".temp suffix", but the code uses a tmp/ folder.
